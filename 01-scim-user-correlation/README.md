\# SCIM Duplicate-Account Troubleshooting Lab



\## Overview



This lab simulates a common IAM/IGA integration problem: a Joiner workflow attempts to create a SCIM account, but the target application returns `409 Conflict` because an account with the same username already exists.



The lab uses free local tools to demonstrate SCIM requests, account discovery, identity correlation, troubleshooting, and duplicate-account prevention.



\## Learning objectives



\- Understand the purpose of common SCIM attributes.

\- Send SCIM requests using Postman.

\- Interpret HTTP `200` and `409` responses.

\- Investigate an existing account before provisioning.

\- Identify an identity-correlation failure.

\- Recommend a safe remediation process.

\- Document an IAM integration problem using Git.



\## Tools



\- Postman Free

\- Mockoon

\- Git

\- Windows Notepad or another text editor



\## Scenario



A Joiner workflow attempts to provision the following user:



```json

{

&#x20; "schemas": \[

&#x20;   "urn:ietf:params:scim:schemas:core:2.0:User"

&#x20; ],

&#x20; "externalId": "84721",

&#x20; "userName": "marcela.braga@example.com",

&#x20; "active": true

}

```



The target application rejects the request because an account with the same `userName` already exists.



The objective is to investigate the conflict, determine why the existing account was not correlated, and recommend a safe solution without creating a duplicate account.



\## Relevant SCIM concepts



SCIM is a standard used to exchange identity information and manage accounts across systems.



Important attributes in this lab include:



\- `id`: A unique identifier generated by the target application.

\- `externalId`: An identifier supplied by the client, usually based on an authoritative source such as an HR employee ID.

\- `userName`: The user’s login name, which is normally unique.

\- `active`: The current status of the account.

\- `emails`: The email addresses associated with the account.



A `409 Conflict` with the SCIM error type `uniqueness` means that the provisioning request contains a value that conflicts with an existing resource.



Before creating an account, an IGA workflow should search for existing accounts and apply its correlation rules.

1\. Start the local SCIM API in Mockoon.

\## Test 1: Provision the account



\### Request



```http

POST http://127.0.0.1:3001/scim/v2/Users

Content-Type: application/scim+json

```



\### Result



The provisioning request returned `HTTP 409 Conflict`.



```json

{

&#x20; "schemas": \[

&#x20;   "urn:ietf:params:scim:api:messages:2.0:Error"

&#x20; ],

&#x20; "status": "409",

&#x20; "scimType": "uniqueness",

&#x20; "detail": "A user with this userName already exists"

}

```



The response indicates that the requested `userName` is already associated with an account in the target application.



\## Test 2: Search for the existing account



\### Request



```http

GET http://127.0.0.1:3001/scim/v2/Users?filter=userName%20eq%20%22marcela.braga%40example.com%22

```



The unencoded SCIM filter is:



```text

userName eq "marcela.braga@example.com"

```



\### Result



The search returned `HTTP 200 OK` with one matching resource.



```text

totalResults: 1

id: a9f1c270

externalId: EMP-0084721

userName: marcela.braga@example.com

active: true

```



\## Attribute comparison



| Attribute | Joiner request | Existing account |

|---|---|---|

| `externalId` | `84721` | `EMP-0084721` |

| `userName` | `marcela.braga@example.com` | `marcela.braga@example.com` |

| `active` | `true` | `true` |



\## Diagnosis



The provisioning request returned `409 Conflict` because an account with the same `userName` already existed in the target application.



The Joiner request used `84721` as its `externalId`, while the existing account used `EMP-0084721`. This formatting difference may have prevented the IGA platform from correlating the account before attempting to create it.



The existing account cannot be considered a different person based only on the `externalId` mismatch. It may represent the same employee using a prefix and zero-padding convention.



\## Proposed remediation



Before linking the account, its ownership should be validated using:



\- The authoritative HR record.

\- The employee ID.

\- The username and email address.

\- The account creation and modification history.

\- The employee’s current lifecycle status.

\- Any previous identity or account correlation records.



If the records represent the same person, the existing account should be reconciled with the identity instead of creating another account.



The transformation and correlation logic should also be updated so that employee IDs use a consistent format. For example, employee ID `84721` could be transformed into `EMP-0084721` before correlation.



The workflow should search for an existing account before sending a `POST` request. A username or email address may be used to identify possible matches, but a stable authoritative identifier should be required for automatic correlation.



\## Security considerations



Accounts should not be linked automatically using only a matching name or email address. Incorrect identity correlation could give one person access to another person’s account.



Any manual reconciliation should be validated, approved, and recorded for audit purposes.



The lab uses fictional information and does not contain:



\- Real employee information.

\- Company information.

\- Passwords.

\- Access tokens.

\- API secrets.

\## What I learned



A `409 Conflict` is not only a provisioning failure. It may indicate that account discovery or identity correlation failed before provisioning.



Consistent identifier formats are essential for reliable identity correlation. A workflow should search for existing accounts, normalize authoritative identifiers, and verify ownership before creating or linking accounts.



This approach helps prevent duplicate accounts, incorrect identity correlation, unauthorized access, and audit issues.
